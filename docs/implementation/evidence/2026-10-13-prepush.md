## Blocking production issues retained by the rollback

1. The connected application database still reports the old schema. The new manual-week workflow is guarded until the operational schema and approved catalog mappings are ready. A source push alone does not enable it.
2. The restored Ranking UI expects `score`/`badges`, while the operational Ranking API returns `orderValue`/unknown-balance data. A nonempty operational response can break the restored UI (`src/app/ranking/page.tsx:299`, `src/app/api/ranking/route.ts:16`).
3. Restored web/native Reports expects legacy summaries and section names, while the operational reporting service returns `cycleReports`, `overall`, `products` and paginated receivable items (`src/app/reports/page.tsx:391`, `mobile/app/reports/index.tsx:102`, `src/lib/services/reports.ts:51`). This is source-verified compatibility risk, not a failure observed against the currently connected legacy schema.

The user's rollback was preserved exactly; no data-contract repair or new tab layout was silently reintroduced. The earlier missing-cost/assumed-stock and installment-reminder issues in the restored legacy report logic also remain unresolved. A future fix can retain the restored UI while repairing data contracts/calculations.

The release runbook still requires approved catalog mapping, tested backups and historical reconciliation, real admin/nonadmin and Data API/RLS acceptance, and physical iPhone/Android checks. Review-branch push readiness is distinct from production approval.
